## 「新闻」分类

## 抓取 ≠ 导入（回答「1-2 小时 vs 试验 1,000 篇」）

这是两件事，之前没说清楚：

| | 做什么 | 碰数据库吗 | 耗时 |
|---|---|---|---|
| **抓取 fetch** | 从旧站下载 15,513 篇 → 写成一个 JSON 文件 | **完全不碰** | 1–2 小时（走代理，慢） |
| **导入 import** | 读那个 JSON → 写进数据库 | 会写 | 几分钟 |

慢的是抓取，而抓取是只读的、可以重跑的、出错也不会损坏任何东西。
所以：**抓一次，分批导入**——先导 1,000 篇看结果对不对，确认后再导其余的。
不是抓两次。

抓之前我会先抓 200 篇试一下（`--max-posts 200`，约两分钟），
确认分类字段、正文、日期都正常，再启动全量抓取。

## 现有 10,000 篇怎么办（回答第 4 题）

**不用删，也不会有停机。**

- **抓取期间**：网站完全不受影响——抓取只写文件。
- **导入时**：导入脚本按 `(slug, locale)` 覆盖写入，并且**会先删掉这篇文章原有的分类
  关联再写新的**。所以同一篇文章重新导入一次，分类就被就地改正了，不需要先清空。
- 现有 10,000 篇的 `legacy_id` 都在新的 15,513 篇里，是子集关系，不会有孤儿。

具体做法：
```
npm run migrate:import -- artifacts/phase5/normalized-full.json --apply --update-existing
```
`--update-existing` 是关键：不加它，已存在的文章会被跳过，分类也就不会被修正。

导入完成后再核对一次分类篇数。只有在核对出问题、需要从干净状态重来时，才考虑清空。

> **两个刚修掉的坑**（否则重导会出事）：
> 1. 导入脚本原本会把每个分类的名字覆盖成由 slug 生成的英文——
>    重导一次，「红朝败相」就会被改回 "Red Regime Collapse"。现在只创建缺少的分类，
>    已存在的名字一律不动。
> 2. 取消兜底之后，匹配不到分类的文章 `category` 为空；原本会被造出一个
>    「untitled」分类。现在遇到这种行直接中止导入，并提示先跑覆盖检查。

## 步骤

**第 0 步 · 代码准备（已完成）**
- 对照表按 51 个真实分类重写，覆盖率 100%
- **取消兜底**：匹配不到的文章不再被塞进「新闻」，而是在覆盖检查里报出来
- 归一化时**保留原始 WP 分类**（`wpCategories` 字段）——上次就是丢了它，导致事后无法核对

**第 1 步 · 全量重新抓取**
```
WP_BASE_URL="https://www.tuidang.org" npm run migrate:wp -- --per-page 20 > artifacts/phase5/normalized-full.json
```
不加 `--max-posts`，抓满 15,513 篇。走代理会慢，预计一两个小时。

**第 2 步 · 覆盖检查**
```
npx tsx scripts/check-wp-taxonomy.ts --rest https://www.tuidang.org
```
必须是「未覆盖 0」才继续。

**第 3 步 · 试验导入 ≤1,000 篇**
```
npm run migrate:import -- artifacts/phase5/normalized-full.json --dry-run
```
先 dry-run 看分类分布对不对，再小批量 `--apply` 一千篇，检查：
各分类篇数、`section=resources` 是否真的分出来了、301 跳转是否正确。

**第 4 步 · 全量导入（覆盖写入，不清空）**
```
npm run migrate:import -- artifacts/phase5/normalized-full.json --apply --update-existing
```
现有 10,000 篇会被就地更新（含分类），另外 5,500 篇新增。全程网站可用。
导入前仍建议导出一份现有 `cms_articles` 备份，以防万一。

**第 5 步 · 收尾**
核对各分类篇数与上表是否一致；确认「新闻」为 0 篇后删掉它；重建跳转表。

> 第 4 步是覆盖写入，不是删除，风险比原计划低得多；但仍建议先备份。
> 只有在导入后核对不通过、需要从零重来时，才清空重导。

## 三个追加问题的答复（2026-09-29）

### 1. 「未分类」要不要建？—— 要，但理由比「减少困惑」更硬

不建的话，那 **651 篇会根本不被导入**，于是它们的旧网址在上线后**全部 404**——
跳转表是从导入数据生成的，没导入就没有跳转。这 651 篇是：

245 视频精选 · 230【视频系列】三退大潮 · 99 希望的路 · 31 未分类 · 22 退党洪流 ·
9 九评共产党 · 6 其他 · 4 temp · 3 其他视频 · 2 真相广播

所以现在建一个 **「待归类」`unfiled`** 分类，它们照常导入、网址照常可用，
之后在后台批量改分类即可。

**它不是兜底。** 区别很重要，上一次 7,785 篇出事正是因为有兜底：

| 情况 | 处理 |
|---|---|
| 旧分类**在对照表里**，但我们还没决定去处（视频系列、未分类、temp） | 进「待归类」，导入 |
| 旧分类**不在对照表里** | **中止导入**并报出来 |

第二条是安全网，保留不动。

### 2. 先做后台还是先抓数据？—— 同时做，抓取不用人看着

抓取是无人值守的：它只下载、写文件，不碰数据库，网站照常运行。所以：

- **现在启动全量抓取**（后台跑着），同时开始做文章管理后台。
- 两者不冲突：后台要加的字段（副标题、封面、作者）是 `cms_articles` 新增列，
  迁移导入只写它已有的那些列，互不干扰。
- **先抓的理由**：抓取是唯一还有未知数的环节，越早暴露问题越好；
  后台的工作量是可预估的。而且拿 15,513 篇真实数据做出来的列表、筛选、分页，
  比拿 200 篇试验数据靠谱得多——很多问题只有上量才看得出来。

距离上线两周，建议顺序：抓取（后台跑）→ 迁移 010 → 新建/编辑页 → 查找与批量改分类 →
最新 100 篇 → 统计。前四步做完就能发稿，也能开始给「待归类」和大分类归位。

### 3. 两周后能不能只抓新文章？—— 能，已经做好了

WordPress REST 支持按时间过滤，脚本已加两个参数：

```bash
# 只抓某日之后新发布的
npx tsx scripts/migrate-wp-posts.ts --after 2026-09-29T00:00:00 > new.json

# 连同期间被修改过的旧文一起抓（补稿、改错字）
npx tsx scripts/migrate-wp-posts.ts --modified-after 2026-09-29T00:00:00 > changed.json
```

实测：`--after 2026-09-20` 只回来 32 篇（2026-09-23 起），几秒钟完成。

导入时用 `--update-existing`，按 `(slug, locale)` 覆盖写入：新文章新增，
改过的旧文更新，没动过的不变。**上线前再跑一次增量即可，不需要重抓一万五。**

建议上线当天早上跑一次 `--modified-after`，把两周内的新增与修改一次补齐。
