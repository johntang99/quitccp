# 自检与报警：怎么知道防护还在

> 写于 2026-10-15。10 月 13 日那场 DDoS 之后，三天里加了五十多个提交的防护措施。
> 这份文档讲的是**怎么知道它们还在生效**，以及出事时怎么被通知到。

---

## 为什么需要这个

攻击期间加的每一道防护，坏掉的时候都**不报错**：

| 防护 | 悄悄坏掉的样子 | 原来谁会发现 |
| --- | --- | --- |
| 文章页走 CDN 缓存 | 某个组件里新加了一句 `cookies()`，整棵树退出静态渲染，每次请求又去查数据库 | 没人。直到下一次洪水打穿数据库 |
| 媒体走 R2 | `NEXT_PUBLIC_MEDIA_MIRROR_HOST` 在某次重新部署里丢了 | 没人。图片照样显示，只是全走回 Supabase |
| 上传时复制进 R2 | R2 的密钥过期 | 没人。编辑看不出任何区别 |
| 搜索 5 秒上限 | 迁移被回滚，或者 `grant` 丢了 | 没人。搜索照样能用，只是不再有时限 |

共同点是**页面还是好的**。所以缺的不是错误处理，是一个会主动去看一眼的东西。

后台原本已经有这个习惯 —— 「登记册同步」和「站内搜索」两块面板，各带一个状态
徽章和一段出问题时的中文排查步骤。这次做的是把上面这几项也纳进来，再加上邮件。

## 两个入口，一份定义

```
                    ┌─────────────────────────────┐
                    │  lib/admin/defense-status   │  ← healthy 的定义只有这一份
                    │       getDefenseStatus()    │
                    └──────────────┬──────────────┘
                                   │
          每小时第 9 分  Vercel Cron │
                                   ▼
                    ┌─────────────────────────────┐
                    │  /api/cron/selfcheck        │
                    │   1. 跑探针                  │
                    │   2. 存一份结果              │──┐
                    │   3. 该发信就发信             │  │
                    └─────────────────────────────┘  │
                                                     │  cms_site_settings
                    ┌─────────────────────────────┐  │  ops.selfcheck.report
                    │  /admin/dashboard「站点防护」 │◀─┘
                    │   只读上面存的那一份          │
                    └─────────────────────────────┘
```

**面板不自己测量。** 两个原因。探针要发外部请求、最坏等 8 秒，不该放在一个只是
来改错别字的编辑面前。更重要的是：一个自己独立测量的面板，可能和刚刚发出去的那封
报警邮件**结论不一致** —— 那种事后谁也说不清的矛盾。所以 cron 测量，面板报告，
并且把时间戳显示出来，这样一个**已经停止刷新的面板看起来就是停的**，而不是健康的。

## 六项探针

| 探针 | 怎么验 | 走哪条路 |
| --- | --- | --- |
| 媒体镜像开关 | 读运行时 `mirrorRewrite()` | 0 成本 |
| 最近上传已进镜像 | 取 `cms_media_assets` 最新 3 行，HEAD `media.tdinfo.org` | Cloudflare |
| 搜索 5 秒上限 | 调 `search_articles_body`，用一个长到能用索引但匹配不到的词 | Supabase REST |
| 防火墙挑战 | 请求公开首页，**期望**被挡 | Vercel 边缘 |
| 文章页走 CDN 缓存 | 取一篇已发布文章，读 `x-vercel-cache` | Vercel 边缘 |
| 页面图片指向镜像 | 同一个响应的 HTML 里，数镜像地址 vs Supabase 地址 | （同上，一次请求两用） |

### 为什么探针尽量不碰我们自己的公开页面

最直觉的做法 —— 请求几个自己的网址看返回什么 —— 在攻击期间**走不通**，这一点值得
写下来，否则以后看着像 bug。2026-10-15 实测：

```
https://www.tuidang.org/            429   x-vercel-mitigated: challenge
https://<deployment>.vercel.app/    302   -> Vercel SSO 登录页
```

公开域名会挑战一切不是真实浏览器的请求 —— 这正是它的全部意义；部署 URL 又挡在
Deployment Protection 后面。两个地址都给不出有用的答案。

所以探针分成两类。多数直接读数据库或问 Cloudflare，完全不需要请求我们自己。
剩下两项确实需要一个真实渲染过的页面，它们照样会去试，被挑战页挡住时降级成
**「测不到」，而不是「坏了」**。面板上「测不到」是灰色而不是红色，就是这个道理。

### 顺手捡到的一个探针

障碍本身变成了探针：挑战规则开着的时候，服务器端的普通请求一定被 429 挡回来。
**拿到页面反而说明规则不在前面了。** 所以「防火墙挑战」这一项期望的是被拒绝。

它只报「注意」，从不报「出问题」，cron 也不为「注意」发信 —— 因为攻击结束后
把挑战关掉是**有人主动做的决定**，而一个会因为预期内的变更而响的警报，正是人们
学会无视警报的原因。

## 怎么做到不刷屏

一个每小时跑的任务，只要有问题就发信，一件坏事会发出 24 封；到第二天就没人点开了。
所以它**只在状态发生变化时发信**，而不是在状态为坏时发信：

| 情形 | 动作 |
| --- | --- |
| 出现了上一次没有的问题 | 发信 |
| 同一个问题，满 24 小时 | 发信，每天一次 |
| 同一个问题，不到 24 小时 | **什么都不发** |
| 之前有问题，现在全好了 | 发一封「已恢复」 |

只有「出问题」算。「注意」不算（见上面那段）。上一次的结论存在
`cms_site_settings` 的 `ops.selfcheck.state` —— 那张表本来就是 service_role 专用的
键值表，所以**不需要加迁移**。代价是这个键会出现在 `/admin/settings` 的列表里，
和可编辑的设置项并列；无害，而且比藏起来好。

四条分支在 2026-10-15 都实测过：`new` / 抑制 / `reminder` / `recovered` 都符合预期。

## 邮件走 Resend

`RESEND_API_KEY` 本来就在环境变量里，而且**一行代码都没用过** —— 这是第一个用它的
地方。现在项目唯一的邮件（重置密码）走的是 Supabase Auth，但那是用它自己的模板发给
一个已存在的账号；报警两样都不是。

**这把 key 下已验证的发信域名属于同一账户里的别的站点**，所以 `RESEND_FROM` 是一个
baamplatform.com 的地址，不是 tuidang.org。给自己发的运维邮件无所谓，但
**任何读者会收到的邮件都不要复用它**。

| 变量 | 值 | 没配会怎样 |
| --- | --- | --- |
| `RESEND_API_KEY` | （已有） | 不发信，日志里一行 warn |
| `RESEND_FROM` | `Quitccp<support@baamplatform.com>` | 同上 |
| `ALERT_EMAIL_TO` | `john.tang2025@gmail.com` | 同上 |

发信失败**不会**让自检任务失败。一个把被它监控的任务搞崩的报警，比没有报警更糟。

## 要在 Vercel 上做的两件事

### 1. 环境变量 `ALERT_EMAIL_TO`

Production 环境加上收件人地址。另外三个（`RESEND_*`、`CRON_SECRET`）已经在了。

### 2. 一条防火墙放行规则（可选，但值得做）

不加这条，面板上「文章页走 CDN 缓存」和「页面图片指向镜像」会一直显示
「测不到」—— 不会误报，但也不会告警。而这两项恰恰是**唯一会悄无声息坏掉**的两项。

Vercel → 项目 → Firewall → 新建规则，放在那条 Challenge 规则**上面**：

| | |
| --- | --- |
| If | Request Header　`x-quitccp-probe`　equals　`<一串随机字符串>` |
| Then | **Allow** |

然后把同一串字符串加成环境变量 `PROBE_BYPASS_SECRET`。

这不是任何东西的后门：这个请求头只影响 Vercel 的防火墙要不要挑战这个请求，
而它能访问到的页面就是每个读者本来就能拿到的公开页面。

---

## 刻意没放进来的东西

**防火墙规则本身，和攻击流量曲线。** 读这些需要一个 Vercel API token，环境里没有；
而且它们是唯一已经显示在有人会看的控制台里的部分。这套自检补的是**原来没人在看的
那一半**。

**Log Drain 归档。** Worker 代码在 `workers/vercel-log-drain/`，桶也建好了，
但还没部署，所以没有可检查的对象。部署之后值得加一项探针。

## 怎么用

| 想做的事 | 怎么做 |
| --- | --- |
| 看现在的状态 | `/admin/dashboard` →「站点防护」（只有 super_admin / content_admin 看得到） |
| 修完之后立刻重测 | 同一块面板上的「立即检查」 |
| 确认报警链路通畅 | 「试发报警邮件」。它不改动存下来的状态 |
| 自检本身停了 | 面板会说。超过 3 小时没刷新就提示去看 Vercel 的 Cron Jobs |

面板**不显示给编辑**。一个编辑看到「文章页走 CDN 缓存：MISS」既做不了什么，又会
合情合理地理解成「网站坏了，先别发布」—— 和「强制刷新全站缓存」那个按钮不给编辑
是同一个道理。
