# 自检与报警：怎么知道防护还在

> 写于 2026-10-15。10 月 13 日那场 DDoS 之后，三天里加了五十多个提交的防护措施。
> 这份文档讲的是**怎么知道它们还在生效**，以及出事时怎么被通知到。

---

## 为什么需要这个

攻击期间加的每一道防护，坏掉的时候都**不报错**：

| 防护 | 悄悄坏掉的样子 | 原来谁会发现 |
| --- | --- | --- |
| 文章页走 CDN 缓存 | 某个组件里新加了一句 `cookies()`，整棵树退出静态渲染，每次请求又去查数据库 | 没人。直到下一次洪水打穿数据库 |
| 媒体走 R2 | `NEXT_PUBLIC_MEDIA_MIRROR_HOST` 在某次重新部署里丢了 | 没人。图片照样显示，只是全走回 Supabase |
| 上传时复制进 R2 | R2 的密钥过期 | 没人。编辑看不出任何区别 |
| 搜索 5 秒上限 | 迁移被回滚，或者 `grant` 丢了 | 没人。搜索照样能用，只是不再有时限 |

共同点是**页面还是好的**。所以缺的不是错误处理，是一个会主动去看一眼的东西。

后台原本已经有这个习惯 —— 「登记册同步」和「站内搜索」两块面板，各带一个状态
徽章和一段出问题时的中文排查步骤。这次做的是把上面这几项也纳进来，再加上邮件。

## 两个入口，一份定义

```
                    ┌─────────────────────────────┐
                    │  lib/admin/defense-status   │  ← healthy 的定义只有这一份
                    │       getDefenseStatus()    │
                    └──────────────┬──────────────┘
                                   │
          每小时第 9 分  Vercel Cron │
                                   ▼
                    ┌─────────────────────────────┐
                    │  /api/cron/selfcheck        │
                    │   1. 跑探针                  │
                    │   2. 存一份结果              │──┐
                    │   3. 该发信就发信             │  │
                    └─────────────────────────────┘  │
                                                     │  cms_site_settings
                    ┌─────────────────────────────┐  │  ops.selfcheck.report
                    │  /admin/dashboard「站点防护」 │◀─┘
                    │   只读上面存的那一份          │
                    └─────────────────────────────┘
```

**面板不自己测量。** 两个原因。探针要发外部请求、最坏等 8 秒，不该放在一个只是
来改错别字的编辑面前。更重要的是：一个自己独立测量的面板，可能和刚刚发出去的那封
报警邮件**结论不一致** —— 那种事后谁也说不清的矛盾。所以 cron 测量，面板报告，
并且把时间戳显示出来，这样一个**已经停止刷新的面板看起来就是停的**，而不是健康的。

## 七项探针

| 探针 | 怎么验 | 走哪条路 |
| --- | --- | --- |
| 媒体镜像开关 | 读运行时 `mirrorRewrite()` | 0 成本 |
| 最近上传已进镜像 | 取 `cms_media_assets` 最新 3 行，HEAD `media.tdinfo.org` | Cloudflare |
| 搜索 5 秒上限 | 调 `search_articles_body`，用一个长到能用索引但匹配不到的词 | Supabase REST |
| 日志存档 | 列最近三个小时的 R2 前缀，看有没有新批次 | Cloudflare |
| 文章页走 CDN 缓存 | 取**最近改过**的那篇文章，读 `x-vercel-cache` | Vercel 边缘 |
| 页面内容是最新的 | 同一份 HTML 里有没有这篇文章在数据库里的当前标题 | （同上） |
| 页面图片指向镜像 | 同一份 HTML 里数镜像地址 vs Supabase 地址，再抽一个 HEAD 一下 | （同上，一次请求三用） |

取「最近改过」而不是「最近发布」的那篇，是因为只有它的新鲜度说明得了问题：
一篇一周没人动过的文章，就算清缓存早就坏了，它的页面也会和数据库一致。

「页面内容是最新的」补的是一个外面看不出来的故障：**缓存着的旧内容，和缓存着的
正确内容，从外面长得一模一样**。保存时的 `revalidatePath` 一旦不触发，编辑的改动
就永远不会出现在网站上，而且不报任何错。这件事以前坏过。

### 为什么探针尽量不碰我们自己的公开页面

最直觉的做法 —— 请求几个自己的网址看返回什么 —— 在攻击期间**走不通**，这一点值得
写下来，否则以后看着像 bug。2026-10-15 实测：

```
https://www.tuidang.org/            429   x-vercel-mitigated: challenge
https://<deployment>.vercel.app/    302   -> Vercel SSO 登录页
```

公开域名会挑战一切不是真实浏览器的请求 —— 这正是它的全部意义；部署 URL 又挡在
Deployment Protection 后面。两个地址都给不出有用的答案。

所以探针分成两类。多数直接读数据库或问 Cloudflare，完全不需要请求我们自己。
剩下三项确实需要一个真实渲染过的页面，它们照样会去试，被挑战页挡住时降级成
**「测不到」，而不是「坏了」**。面板上「测不到」是灰色而不是红色，就是这个道理。

### 为什么没有「防火墙还在挑战吗」这一项

做过一个。它不带放行请求头去请求首页，期望被拒绝 —— 在放行规则存在之前一直好用，
规则上线之后每次都报「未挑战（HTTP 200）」，而防火墙明明还在挡所有别的请求。
2026-10-15 实测：同一个请求，从笔记本发出去是 429，从函数里发出去是 200。

原因是 bot protection 主要看 TLS 指纹、在**建立连接时**判定，而 Node 的 fetch 会
复用连接池。这个文件里别的探针正带着放行请求头在同一个池子上跑，等这个不带头的
请求出去时，它骑的已经是一条边缘放行过的连接。**一个进程没法一边发特殊请求、
一边问「普通请求会得到什么」。**

防火墙自己的状态用 `vercel firewall status` 看，那才是它该待的地方。

## 怎么做到不刷屏

一个每小时跑的任务，只要有问题就发信，一件坏事会发出 24 封；到第二天就没人点开了。
所以它**只在状态发生变化时发信**，而不是在状态为坏时发信：

| 情形 | 动作 |
| --- | --- |
| **连续两次**都坏的问题，且上次没报过 | 发信 |
| 同一个问题，满 24 小时 | 发信，每天一次 |
| 同一个问题，不到 24 小时 | **什么都不发** |
| 之前有问题，现在全好了 | 发一封「已恢复」 |

**连续两次，不是一次。** 这套东西第一次发出去的警报就是个假警报：2026-10-15，
放行规则刚上线的那一次运行，文章页连着两次 MISS —— 因为在那之前没有任何请求走过
这条路，缓存是凉的；下一次运行、以及之后每一次，都是 HIT。什么事都没有。
对这些本来就是「静悄悄坏掉」的故障来说，晚一小时通知没有任何代价，而这一小时
正是信号和抖动的分界线。

只有「出问题」算。上一次的结论存在
`cms_site_settings` 的 `ops.selfcheck.state` —— 那张表本来就是 service_role 专用的
键值表，所以**不需要加迁移**。代价是这个键会出现在 `/admin/settings` 的列表里，
和可编辑的设置项并列；无害，而且比藏起来好。

四条分支在 2026-10-15 都实测过：`new` / 抑制 / `reminder` / `recovered` 都符合预期。

## 邮件走 Resend

`RESEND_API_KEY` 本来就在环境变量里，而且**一行代码都没用过** —— 这是第一个用它的
地方。现在项目唯一的邮件（重置密码）走的是 Supabase Auth，但那是用它自己的模板发给
一个已存在的账号；报警两样都不是。

**这把 key 下已验证的发信域名属于同一账户里的别的站点**，所以 `RESEND_FROM` 是一个
baamplatform.com 的地址，不是 tuidang.org。给自己发的运维邮件无所谓，但
**任何读者会收到的邮件都不要复用它**。

| 变量 | 值 | 没配会怎样 |
| --- | --- | --- |
| `RESEND_API_KEY` | （已有） | 不发信，日志里一行 warn |
| `RESEND_FROM` | `Quitccp<support@baamplatform.com>` | 同上 |
| `ALERT_EMAIL_TO` | `john.tang2025@gmail.com` | 同上 |

发信失败**不会**让自检任务失败。一个把被它监控的任务搞崩的报警，比没有报警更糟。

## 要在 Vercel 上做的两件事

### 1. 环境变量 `ALERT_EMAIL_TO`

Production 环境加上收件人地址。另外三个（`RESEND_*`、`CRON_SECRET`）已经在了。

### 2. 一条防火墙放行规则（可选，但值得做）

不加这条，面板上「文章页走 CDN 缓存」「页面内容是最新的」「页面图片指向镜像」
会一直显示「测不到」—— 不会误报，但也不会告警。而这三项恰恰是**唯一会悄无声息
坏掉**的几项。面板上「测不到」这一格里会写明配置方法，不用回来翻文档。

Vercel → 项目 → Firewall → 新建规则，放在那条 Challenge 规则**上面**：

| | |
| --- | --- |
| If | Request Header　`x-quitccp-probe`　equals　`<一串随机字符串>` |
| Then | **Allow** |

然后把同一串字符串加成环境变量 `PROBE_BYPASS_SECRET`。

这不是任何东西的后门：这个请求头只影响 Vercel 的防火墙要不要挑战这个请求，
而它能访问到的页面就是每个读者本来就能拿到的公开页面。

## 刻意没放进来的东西

**防火墙规则本身，和攻击流量曲线。** 读这些需要一个 Vercel API token，环境里没有；
而且它们是唯一已经显示在有人会看的控制台里的部分。这套自检补的是**原来没人在看的
那一半**。

**Log Drain 归档。** Worker 代码在 `workers/vercel-log-drain/`，桶也建好了，
但还没部署，所以没有可检查的对象。部署之后值得加一项探针。

## 怎么用

| 想做的事 | 怎么做 |
| --- | --- |
| 看现在的状态 | `/admin/dashboard` →「站点防护」（只有 super_admin / content_admin 看得到） |
| 修完之后立刻重测 | 同一块面板上的「立即检查」 |
| 确认报警链路通畅 | 「试发报警邮件」。它不改动存下来的状态 |
| 自检本身停了 | 面板会说。超过 3 小时没刷新就提示去看 Vercel 的 Cron Jobs |

面板**不显示给编辑**。一个编辑看到「文章页走 CDN 缓存：MISS」既做不了什么，又会
合情合理地理解成「网站坏了，先别发布」—— 和「强制刷新全站缓存」那个按钮不给编辑
是同一个道理。

## 日志：原始的留 14 天，汇总的留一辈子

和上面那些探针是同一个思路的延伸 —— 探针回答「现在正常吗」，日志回答
「刚才发生了什么」和「那阵子正常吗」。

```
Vercel ──drain──▶ Worker ──▶ R2 原始 NDJSON（14 天）
                                │
                                │ 每小时第 12 分 /api/cron/log-rollup
                                ▼
                          cms_log_hourly（Postgres，永久，一天 24 行）
                                │
                                ▼
                          /admin/logs
```

**后台页面读 Postgres，不读 R2。** 一小时的原始日志是几十 MB，每打开一次
页面去下载它是不可接受的；而汇总行一天 24 条、一条几百字节，十年也就 1 MB
左右。所以这个页面一年后还能回答「上周二正常吗」，而「某一条请求长什么样」
用 `scripts/read-drain-logs.mjs` 在 14 天内去查原始记录。

### 字段位置有两个反直觉的地方

对着线上 drain 实测（2026-10-15）：

| 想要的 | 实际在哪 |
| --- | --- |
| 状态码 | `proxy.statusCode` —— **不在顶层** |
| 请求的网址 | `proxy.path` |
| 路由模式 | 顶层 `path`，形如 `videos/[[...slug]]` |
| 缓存结果 | `proxy.vercelCache`（HIT/MISS/STALE/PRERENDER） |
| User-Agent | `proxy.userAgent`，是**数组** |
| TLS 指纹 | 顶层 `ja4Digest` —— 防火墙规则就是按它建的 |

**没有 `proxy` 的那一行根本不是请求。** 构建日志一分钟能产生几百行，混进
请求数里会让每次发布看起来都像一次流量高峰 —— 实测一小时 444 行里有 416 行
是构建日志。所以它们单独计入 `other_lines`。

热门路由统计的是**路由模式**不是具体网址：`news/[slug]` 而不是 15,374 篇
文章里的某一篇。否则每小时的前十名都是十篇不同的文章，看不出流量落在站点
的哪一块。

### 刻意没存的东西

任何从 `proxy.clientIp` 推导出来的数据。本站读者是海外华人，**「谁读了什么」
这种永久可查的记录，不该作为一张流量图的副产品被创建出来**。

2026-10-15 起原始存档里也不再有 IP 了：Vercel 的 IP Address Visibility 拆成
两个开关，「Show in Log Drains」已关闭，「Show in Vercel Dashboard」保持开启
——攻击取证用后者，那些数据只活在 Vercel 自己的保留期里。理由写在
`workers/vercel-log-drain/README.md`，**不要因为看见 drain 里缺 IP 就把它
打开**。

## 防火墙里的两条放行规则

两条都在 **Vercel** 的防火墙里，不在 Cloudflare。`tuidang.org` 在 Cloudflare 上
**只做 DNS**，网站托管在 Vercel；只有 `service`、`santui` 那几个子域是 Cloudflare
代理的。2026-10-15 真的有人照着「请在 Cloudflare 中放行」去找，找不到 —— 判断是
哪一层的办法是看响应头：

```
www.tuidang.org      server: Vercel      没有 cf-ray
service.tuidang.org  server: cloudflare  有 cf-ray
```

| 规则 | 认什么 | 给谁用 |
| --- | --- | --- |
| `Rate limit td-auth proxy` | 反代出口 IP，3000 次/60 秒 | 安全网，见下 |
| `Allow 免翻 reverse proxy v2` | 出口 IP **并且** `td-auth` 请求头 → Bypass | Tom 维护的免翻墙反代 |
| `Allow 免翻 reverse proxy`（旧） | 只认 `td-auth` 请求头 → Bypass | **待删**，见下 |
| `Bypass for selfcheck probe` | `x-quitccp-probe` → Bypass | 本文前面那三项探针 |

**Vercel 的 Bypass 会终止后续全部规则** —— 不只是跳过托管的机器人挑战，而是连
按 ASN 的封禁、按 IP 的 300 次/分限速一起跳过。带着对的请求头等于对全站免检。

反代那条绕不开：一台代理替很多人取页面，第 3 条「Rate limit per IP」的 300 次/分
一下就超，被挑战之后墙内读者就打不开了。所以它必须排在那条限速**上面**；排到
下面去表现和被删掉一样，而且不会有任何报错。

### 已收紧（2026-10-15 晚）

原来的密钥是 4 个字符、在邮件里传过，而带着它的请求对全站免检。Tom 换成了
32 位随机值并提供了出口 IP，所以 v2 规则的两个条件是 **AND**：光知道请求头、
不是从那个 IP 来的，照样被挡。实测过 —— 拿正确的新密钥从别处请求，返回 429。

**切换期间两条规则并存，这是故意的。** 先换规则则 Tom 的 nginx 还没改、免翻立刻
断；先换 nginx 则规则还没改、一样断。所以新规则加在旧规则上面，谁匹配上都放行，
中间始终有通路。

**待办：Tom 确认新密钥生效后，删掉 `Allow 免翻 reverse proxy`（旧）那一条。**
留着它等于那把 4 字符的旧密钥仍然有效。

```bash
npx vercel firewall rules remove "Allow 免翻 reverse proxy"
npx vercel firewall publish
```

### 新增的一种失效方式

IP 绑定换来了安全，也换来一个新的脆弱点：**反代换服务器、出口 IP 变了，规则就
不再匹配**。表现是墙内打不开，而本站这边一切正常、没有任何报错 —— 对我们来说
那只是又一个被挑战的请求。遇到这种情况先问 Tom 现在的出口 IP，再
`rules edit` 改掉。

### 为什么这三条没有对应的自动检查

探针验不了它们。Node 的 fetch 复用连接，而别的探针正带着放行头在同一个连接池上
跑，所以一个不带头的请求会骑在已经放行过的连接上，永远返回正常 —— 测不出规则是
不是被删了。同一个原因让「防火墙还在挑战吗」那项探针被撤掉（见前文）。

所以这件事在后台是**一段写死的说明**，不是一项检查：`/admin/dashboard` →
「防火墙里的两条例外」。免翻墙打不开时，第一件事是
`npx vercel firewall rules list` 看那条规则还在不在、顺序对不对。
