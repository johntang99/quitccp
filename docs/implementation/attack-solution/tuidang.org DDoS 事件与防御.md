# tuidang.org DDoS 事件与防御

Oct 13, 2026 · 记录人 @John · 持续更新 · 最后更新 10-13 深夜

## 事件概要

www.tuidang.org 遭受持续的七层 DDoS 攻击，10 月 13 日凌晨约 2:00（美东）起规模化，峰值 35,000 请求/秒。数据库被打到拒绝连接，站点全线不可用数小时。**截至当晚，攻击仍在以极高强度持续，25 小时内累计 16.6 亿次请求，但已被完全挡住**，站点与数据库正常。

| 项目 | 情况 |
| --- | --- |
| 攻击规模 | 峰值 35,000 req/s；25 小时累计 **16.6 亿次**（上午记录为 3.9 亿，攻击此后仍在加码） |
| 主要靶子 | 单篇 2013 年旧文；当晚发现它还在用**旧 WordPress 地址**绕过规则 |
| 直接后果 | Postgres 连接耗尽、全线 522，站点不可用数小时 |
| 账单影响 | 当晚 $181.35 / $200（上限的 91%）；WAF 挡下的流量不计费 |
| 当前状态 | 攻击持续中，防线挡住；数据库查询 0.26～0.58 秒 |

## 攻击画像

这是一场分布式的七层 HTTP Flood，目标不是带宽而是后端资源；它使用随机查询参数绕过 CDN 缓存，强迫每一个请求都回源执行函数。

| 维度 | 实测数据 |
| --- | --- |
| 总量 | 16.6 亿次（25 小时窗口，当晚） |
| 峰值 | 35,000 req/s |
| 集中程度 | 单篇文章占压倒多数，首页次之 |
| 主要来源 AS | 3xK Tech GmbH (AS200373) 2.655 亿次 |
| TLS 指纹 | 单一 JA4 `t13d1511h2_8daaf6152771_5b3554b5c573` 3.314 亿次 |
| 地理分布 | 德国 1.872 亿、美国 1.639 亿、加拿大 9,100 万 |
| 请求方法 | GET / HEAD / POST 均匀混用（本站无 Server Action，POST 必定非法） |
| 缓存绕过 | 每请求挂随机 `rnd=` 参数 |
| User Agent | 轮换 Chrome 121/133/134/135/136、Android 14 |

### 两个最能说明问题的数字

**验证通过率 337 / 15.4 亿。** 25 小时内发出 **15.395 亿次** JavaScript 验证，只有 337 次被通过、120 次失败——也就是说这些机器人连试都不试。这 15 亿次请求里几乎没有一个是人。

**HTML 与 CSS 的比例。** 真浏览器打开页面必然加载 CSS。被攻击文章的 HTML 请求数是 CSS 的十万倍量级，这是「它们不是浏览器」的铁证，但它是统计层面的，而防火墙逐个请求判断，用不上。

## 因果链：数据库为什么会倒

数据库不是自己坏的，是被一条放大链条拖倒的。关键在于每一环都把上一环的压力放大，而不是吸收。

1. 每秒数百至数万请求打同一个地址。
2. 文章页是全站唯一完全不缓存的页面类型（`cache-control: no-store`），所以每一个请求都真实调用函数、真实查数据库。
3. 数据库是 MICRO 规格（t3a.micro），**最大连接数只有 60**，很快被占满。
4. 查询开始排队变慢，请求卡住。
5. 内容路由从未设过 `maxDuration`，因此继承 Vercel 的 **300 秒**上限——每个卡住的函数把数据库连接死死占住整整五分钟不释放。
6. 新请求持续涌入，连接池永远排空不了。
7. Postgres 停止接受连接 → REST、Auth、Storage 全线 522/544。

12 小时内 Vercel 记录了 **86,000 次 `FUNCTION_INVOCATION_TIMEOUT`**，每次都是 `5m / 5m` 跑满。账单上 `Fluid Active CPU 449 小时` 和 `Provisioned Memory 3,190 GB·小时` 就是这来的。

### Supabase 那 2,900 万次错误是结果，不是原因

Supabase 控制台显示 2,900 万次请求、成功率 1%。但站点正常流量只有 **0.6～0.7 请求/秒**（约 6 万/天），差了两个数量级。那 2,900 万几乎肯定是 Postgres 死掉后，Supabase 内部服务（PostgREST / GoTrue / Storage）疯狂重连造成的放大。

**排查时容易走的弯路：** 指标里量最大的那个数字往往是症状而非原因。应该先问「这个量级和我们的真实流量对得上吗」。

## 全部防御手段清单（共 17 项）

按重要性排序。**第 1 项和第 2 项的区别最值得理解**：网络层挡的是「量」，静态化挡的是「每一个漏网请求能造成多大伤害」。两件事，缺一不可——凌晨那次之所以从「变慢」演变成「宕机数小时」，正是因为第 1 项当时不存在。

| --- | --- | --- | --- | --- |

| 4 | **Challenge 旧地址**（10-13 深夜新加） | 我们 | 见下文 | 高，堵上一个还在流血的洞 |
| 5 | Bot Protection = Challenge | 托管规则 | 1,870 万次 | 高，补 JA4 / ASN 规则的盲区 |
| 6 | Challenge secondary JA4 | 我们 | 480 万次 | 中高，另三个次要指纹 |

另：**OWASP 规则集跳过**——它是 Enterprise 付费项（$0.80/百万请求，需联系销售），而且是防注入/XSS 的工具，不是防 DDoS 的。

### 为什么 `maxDuration = 15` 是最关键的一行

对比两次宕机：第一次没有它，必须手动重启项目、耗时数小时；第二次有了它，数据库**五分钟内自行恢复**。差别就在连接释放速度：300 秒 vs 15 秒。

## 关键发现

### 一、封特征赢不了

所有维度都查过，结论是在单个请求层面攻击流量和真实浏览器不可区分。

| 维度 | 为什么封不住 |
| --- | --- |
| 路径 | 封了就换——已实测，封掉那篇文章后 5 分钟改打 `/videos`；深夜又发现它改打旧地址 |
| TLS 指纹 | 被放行流量里最大的指纹只占 17% |
| IP | 被放行流量里最大的 IP 只占 **1.1%** |
| 国家 | 美国 1.64 亿、加拿大 9,100 万——正是真实读者所在地 |
| 机器人分类 | Vercel 分类为 `(not set)`，**根本没识别出它是机器人** |

**有效的是「验证好人」而不是「列举坏人」。** Attack Mode 之所以有效，正因为它不做区分——让所有人证明自己是浏览器。

### 二、静态页面对缓存绕过免疫（已实测）

对已预渲染的页面，Vercel **完全忽略查询参数**：

| 请求 | 结果 |
| --- | --- |
| `/news` | HIT，age 114 |
| `/news?zzz=4irv9cg2be6` | HIT，**age 114**（同一份缓存） |
| `/news?a=1&b=2&c=fga2lux9p8m` | HIT，**age 114** |

这意味着攻击者那套随机参数绕缓存的手法，**对静态页根本无效**。这是静态化方案最大的依据。

### 三、让一个动态路由变成可缓存，需要同时满足三个条件

三个条件缺一不可，而第三个最反直觉，花了最多时间才测出来：

1. 页面签名里**没有** `searchParams`
2. 渲染路径上任何地方**都不调用** `cookies()`
3. **必须有 `generateStaticParams`——哪怕它返回空数组 `[]`**

只缺第三条，路由就仍然是 `ƒ`（动态），响应头仍是 `no-store`，无论 `revalidate` 设成多少都没用。构建输出里 `●` 才算成功，`ƒ` 就是没做到。

### 四、WAF 挡下的流量不计费

Vercel [官方明确说明](https://vercel.com/changelog/web-application-firewall-mitigated-traffic-is-free-on-vercel)：被 WAF **拒绝、质询、限速**的请求，CDN 请求数和流量都免除。

这条很重要，它决定了优化方向：那 15 亿次 challenge 基本不花钱，**账单来自被「放行」的部分**。所以降低成本的办法不是减少攻击，而是让更多攻击流量被挡在 WAF 这一层——这正是第六条发现的价值。

### 五、`app/error.tsx` 救不了静态生成失败

实测确认：当一个静态路由在**按需生成**时失败，Next 会绕过整个 App Router 的错误边界（`app/error.tsx` 和 `app/global-error.tsx` 都不会被用到），回落到 Pages Router 的内置 500 页。

所以项目里新增了 `src/pages/500.tsx`——这是 `app/` 之外唯一的文件，只因为这件事 App Router 答不了。副作用：加入 `pages/` 目录后 `usePathname()` 的类型变为可能为 `null`，`MobileNav` 相应加了判空。

### 六、旧地址是一个被忽略的洞（10-13 深夜发现）

静态化之后看防火墙数据，发现被**放行**的流量里，3 小时内有 **344 万次**打在 `/2013/03/04/23836/`。

这不是普通 404。它正好命中中间件唯一匹配的那个形状（旧 WordPress 链接 `/年/月/日/id/`），所以每一次都要：

```
/2013/03/04/23836/  →  中间件跑一次（查一次 Supabase）
                    →  301 转到 /news/陈思敏：一张照片说出薄熙来与两个赌王不能
```

**是同一篇文章、同一场攻击，换了个旧地址进来。** 原有规则只匹配 `/news/陈思敏…`，匹配不到旧地址，于是一路放行。

加规则后，该路径被放行的量查出来是「No data found」——真的是 0，规则自己命中 142 万次／15 分钟。

**教训：静态化之后要回头重看防火墙的「Allow」那一栏。** 挡住的部分很容易看，漏过去的部分才是还在流血的地方，而且它不计入任何告警。

**另一个教训：判断规则有没有生效，要看规则自己的命中计数，不是看流量降没降。** 第一次加这条规则时，发布后流量正好回落，就当成生效了；实际上那条规则**一次都没匹配上**，洞一直开着（原因见下一条）。攻击流量本来就在剧烈起伏，拿它当证据必然误判。

### 六之二、尾斜杠规范化坑了两次

同一件事，先后以两种面目出现，都花了时间才看清：

**防火墙规则不匹配。** 写的是 `path equals /2013/03/04/23836/`（带尾斜杠），命中数为 0。生效的那条规则路径是 `/news/陈思敏…`（无尾斜杠）。Vercel 的规则引擎把尾斜杠规范化掉了，而**指标里 `requestPath` 那一栏显示的是带斜杠的原始路径**——两边对不上，照着指标抄路径就会写出一条永远不匹配的规则。

做法：用 `--or` 把两种写法都写进去。

```
vercel firewall rules add "名字" \
  --condition '{"type":"path","op":"eq","value":"/路径"}' \
  --or --condition '{"type":"path","op":"eq","value":"/路径/"}' \
  --action challenge --yes
```

**中间件根本没跑。** 实测 `/2013/03/04/23836/` 的真实处理顺序是：

```
/2013/03/04/23836/  →  Next 先用 308 规范化成无尾斜杠
                    →  /2013/03/04/23836  →  这时中间件才跑
```

**308 发生在中间件之前**，所以带尾斜杠的请求压根没碰到中间件，也没碰数据库。这推翻了「每一次都要跑一遍中间件去查库」的判断——那场攻击的实际代价是**被计费的 CDN 请求**，不是数据库压力。

记这一条是因为：涉及路径的任何判断（防火墙条件、中间件 matcher、指标过滤），都要先确认自己看的是规范化前还是规范化后的路径。

### 七、三个被实测推翻的假设

记在这里，是因为它们很像对，下次很容易再犯。

**「健康检查被高频调用打垮了数据库」——错。** `/api/health` 确实有严重缺陷（每次调用触发 5 秒全表扫描，已修），但 Vercel 日志显示它一小时内只被调用 11 次，全是我们自己打的。没有任何外部监控。

**「加 `revalidate = 300` 就能缓存文章页」——错。** 加上后本地生产模式连打三次，响应头纹丝不动，仍是 `no-store`。原因见第三条。

**「生产跑的是旧构建」——错。** 当时只看了 4 个样式表里的第 1 个就下了结论。生产跑的是最新代码；那个看起来很旧的页面是**原型稿里硬编码的兜底内容**，在数据库挂掉后被 ISR 缓存了下来。

**教训：性能与缓存行为必须实测，不能推断。** 判定标准是响应头和计时，不是「按理说应该」。

### 静态化的实测结果

- 文章详情页：首次 1,549ms MISS → 之后 39～113ms HIT
- 20 分钟窗口内，文章详情共进入函数 34 次，分布在 33 个不同地址（平均 1.03 次/地址）
- 视频详情 12 次，分布在 12 个地址（平均 1.00）

也就是**每个地址每个窗口只渲染一次**，其余全部由缓存应答。

### 失败就是失败

`getRenderablePage` 和 `loadRenderableArticle` 的 catch 分支原本会吞掉错误（一个返回原型稿兜底，一个返回 `null` 被路由当成 404）。现在直接抛出。

抛出换来两件事：对已有缓存的页面，Next 的 stale-while-revalidate 会继续发上一份好的副本（几分钟前的**真实**内容），并且绝不把这次失败存进缓存；对没有缓存的页面，显示一个说明情况的错误页，而不是「页面不存在」。

实测（本地生产构建，把 `SUPABASE_URL` 指向死端口）：

| 情况 | 结果 |
| --- | --- |
| 已缓存的 `/` 和 `/news` | HIT，真实内容，非原型稿 |
| 未缓存的三个页面 | 500 + 诚实错误页，非「页面不存在」 |

### 媒体备份

**静态化保住了页面，没保住页面里的媒体。** 缓存页由 Vercel 发出，但里面每张图、每段音频仍写着 `supabase.co`，浏览器要逐个回去取。10-13 那天 Storage 和数据库**一起**返回 544——拿到完好缓存页的读者，看到的仍然是满页裂图。

清点结果：桶里 **8,507 个对象、6.0 GB**，被 6,364 行内容引用，去重后 9,300 个链接，全部只存在那一个出过事的项目里。

### 把数据库从最后两条公开路径上也摘下来

静态化之后，公开路径上还剩两处能走到 Postgres，而且都没有上限：

| 入口 | 问题 |
| --- | --- |
| 中间件 `/年/月/日/<id>/` | 前面两层缓存都按完整 URL 做键，**id 一随机，两层全部失效，每个请求保证一次查询** |
| `/news/a/<id>` | 中间件 301 的终点，但没有任何东西拦着请求**直接**打过来——绕过中间件，同一个终点 |

攻击者已经在用第一个形状了，只是还在用一个固定 id。把 id 随机化就是「用 `rnd=` 参数绕开 CDN」的同一个手法，换到数据库上。限流只能决定这件事发生得多快。

做法：全站只有 **15,526 个** id 能解析成功，delta+base36 编码后 **33 KB**，随中间件一起发出去（中间件 34.6 KB → 48.8 KB）。「这个 id 有没有可能解析成功」这个问题从此不问数据库。

**集合必须是两张表的并集**，这点不能省：`cms_redirects` 是正常情况，但 `cms_articles.legacy_id` 里有 **13 个** id 没有重定向行，靠落到 `/news/a/<id>` 才能解析。只用前者会让 13 个今天还能用的链接 404。

**判断必须放在中间件，不能只放在路由里**——这是量出来才知道的。等到路由能调用 `notFound()` 的时候，布局已经渲染过了，而布局要读主题和导航：**每一个编造的 id 要三次数据库查询**（`cms_site_settings` 两次、`cms_content_entries` 一次）。50 个随机 id 就是 150 次。放到中间件、改写到 Next 预渲染的 404 之后，这三次也没有了——那个 404 页是构建期生成的，查库 0 次。

> 顺带一个反直觉的点：随手打一个垃圾地址（`/abc-123`）查库 **0 次**，因为它没匹配上任何路由，直接吃预渲染的 404。只有「匹配上了某个路由、然后才 `notFound()`」才会付出布局那三次的代价。

实测：

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 50 个随机 id 直接打 `/news/a/` | 150 次查询 | **0 次**，全部 404 |
| 随机 id 走旧地址 | 每个一次查询 | **0 次**，全部 404 |
| 真实 id 走旧地址 | 301 | 301，每个查 1 次 |
| `/news/a/701030`（真实库） | — | 307 → `/news/90后举报习近平…` |
| `/2013/03/04/23836`（真实库） | — | 301 → `/news/陈思敏：一张照片说出薄熙来与两个赌王不能` |

`/news/a/[id]` 同时改为可缓存（`generateStaticParams` 返回空数组 + `revalidate`），构建输出从 `ƒ` 变成 `●`，同一个真实 id 重复进来不再每次查 slug。

**⚠️ 迁移重跑之后必须重新生成，否则新的旧链接会 404：**

```
node scripts/build-legacy-id-set.mjs
```

这条很容易忘，因为忘了不会报错——只是新文章的旧地址静悄悄 404。生成的文件是 `apps/web/src/lib/legacy-redirect-ids.ts`，顶部写着它是生成的、不要手改。

### 还没做：布局那三次查询

上面只是让「编造的 id」不再触发布局渲染。但**任何一次动态渲染都要付那三次**——`/search`、`/about/network`、`/resources/culture`、`/services/faq`、两个分页路由都一样。

彻底的修法是把主题和导航的读取缓存起来（它们很少变）。没有顺手做，是因为那会推迟编辑在后台改导航和主题后看到效果的时间；周五就要切换、编辑还在培训，这种行为变化不该不打招呼就改。要做的话需要同时补上「设置保存后清缓存」，和文章那套失效机制一样。

### 常用排查命令

```
vercel firewall overview          # 总览：各动作总量、各规则命中数、告警
vercel firewall traffic list      # Top IP / JA4 / AS / UA / 路径
vercel firewall status            # 当前配置一览
vercel logs --since 5m --json     # 真正打到函数的流量

# 找出还在被放行的路径（第六条发现就是这么找到的）
vercel metrics vercel.firewall_action.count --since 3h -a count \
  --filter 'action == "allow"' --group-by requestPath --limit 15 --granularity 1h
```

注意 `vercel metrics` 的 `--filter` 用 KQL，写法是 `action == "allow"`（双引号，两个等号）。按 route 分组的函数调用指标需要 Observability Plus 付费项，但上面这条防火墙指标不需要。

**日志保留期很短**：Vercel runtime log 约 1 小时，防火墙分析 25 小时。Oct 11～12 的关键日志已永久丢失。**配 Log Drains 是避免下次重蹈覆辙的唯一办法**（Settings → Log Drains）。

### 每次改完防火墙规则，照这个单子核一遍

1. `vercel firewall rules list` —— 规则在不在、是不是 Enabled
2. 等 10～15 分钟，然后看**规则自己的命中数**：
   ```
   vercel metrics vercel.firewall_action.count --since 15m -a count \
     --filter 'requestPath == "<路径>"' --group-by rule --limit 12 --granularity 15m
   ```
   命中数是 0 就是没匹配上，不管流量降没降
3. 再确认该路径的放行量：把上面的 `--group-by rule` 换成 `--filter '... and action == "allow"'`，期望是 `No data found`
4. 看 `(not set)` 那一栏有没有消失——它代表「没有任何规则匹配」的那部分
